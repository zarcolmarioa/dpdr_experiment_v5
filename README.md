# Derealization experiment (v5b, two blocks)

People who have had episodes of derealization see two edited versions of
the same photograph on each trial and press ← or → to choose the one that
looks more like how their surroundings looked during **one specific
episode**. The two versions differ in local contrast (a "fog"-like
reduction), in colour saturation, or in both. A per-person model then
estimates how strongly each person's choices follow each feature:

```
P(chose A) ~ b_sat · pred_sat + b_fog · pred_fog
```

Each session has **two blocks** of 200 trials (180 analysed, 15
consistency repeats, 5 catch trials), each about a different episode:

| group | episodes (order set by the slot) |
|---|---|
| `participant` | **derealization** (the episode they described in the interview) and **ordinary** (one in a similar setting, about as long ago, in which the surroundings looked as usual) |
| `control` | **ordinary** (an episode from the last six months) and **expectation** (how they think the surroundings look to someone experiencing derealization) |

The question above the images depends on the block's episode. Which
episode comes first, which item set (A / B) goes with which episode, and
the trial order are set per invitation by its **slot** (`?slot=n`, row
((n − 1) mod 64) + 1 of the package's `assignment.json`).

The design is registered. The stimuli, the lists, the assignment table and
the catch targets come from the frozen package **`data/sets/v5b_180/`** and
are never randomised, reordered, resampled or regenerated by the
experiment. Each list is shown in file order, with the sides it gives.

jsPsych 7.1.2, hosted on GitHub Pages with the data uploaded through
DataPipe to Zenodo — or, from the same files, on Pavlovia with the data
kept in the private Pavlovia project (`SETUP.md` §7). See `SETUP.md` for
deployment and `DATA_DICTIONARY.md` for the output.

## The session

The same order for both groups. Length **[TO COMPLETE after pilot]**. Each
step has its own switch in `config.js`.

| # | step | switch |
|---|---|---|
| 1 | Consent — "I do not agree" ends the session, nothing uploaded | `blocks.consent` (**required** on `index.html`) |
| 2 | Full screen and window check — a window that cannot show the trial layout (each of the session's two questions, two 512 px images) whole **stops** the session (no "continue anyway"), before anything is uploaded | `calibration.fullscreen`, `calibration.screen_check` |
| 3 | Participant ID (+ name and email: on GitHub uploaded separately straight away; on Pavlovia kept in the response file). Without an ID in the link: an ID **or** a name and email are required. On Pavlovia the Pavlovia session opens just before this screen | `participant.collect_*`, `participant.allow_manual_id`, `participant.contact_storage` |
| 4 | Brightness confirmation, with a note on night mode / colour filters | `calibration.brightness` |
| 5 | Gamma matching (3×) | `calibration.gamma` |
| 6 | Episode selection — participants: the derealization episode, then an ordinary one; controls: an ordinary episode, then the description of derealization. For each recalled episode: a few identifying words (required) and when / how long / where / emotional tone (−3…+3) / intensity (0–6), each required, each with "Prefer not to say" | `blocks.episodes` |
| 7 | **Block 1** — a reinstatement screen naming the episode with the participant's own words; 3 practice trials with feedback; 200 trials, breaks after 40, 80, 120 and 160 ("n of 200") | `blocks.practice`, `blocks.main` |
| 8 | Rest — 1 minute, countdown; Continue appears at zero | `blocks.rest`, `timing.rest_ms` |
| 9 | **Block 2** — as block 1, with the second episode; its practice intro says the question has changed and shows it | as block 1 |
| 10 | Word ratings — 10 words, 0–6 (participants: the derealization episode; controls: their expectation) | `blocks.words` |
| 11 | State items — 4 items, 0–6 | `blocks.state` |
| 12 | Save (DataPipe / Pavlovia / download), completion screen | `platform` (`'auto'`: from the address) |

The images (≈ 230 MB, both blocks, block 1's first) start downloading in
the background right after the ID screen, so they are usually cached by
the time each block needs them. There are no questions after the blocks.

**Practice** (config.js `practice`, which overrides design.json): 3 trials
before each block, both with feedback — the first 3 rows of
`practice/block1.json` before block 1, the 3 rows of
`practice/block2.json` before block 2. The practice file follows the block
position, not the episode.

**Catch trials** show no images; their targets come from design.json by
block position, restarting in each block. Failures are recorded per block;
the exclusion rule (3 or more over the session) is applied in the
analysis.

## Invitation links

Each participant gets their own link. All parameters are read in the
browser and never reach the server.

```
https://<username>.github.io/<repo-name>/?pid=<ID>&group=<group>&slot=<n>&idate=<YYYY-MM-DD>
https://run.pavlovia.org/<user>/<project>/?pid=<ID>&group=<group>&slot=<n>&idate=<YYYY-MM-DD>
```

The same parameters on both.

| parameter | required | values | notes |
|---|---|---|---|
| `pid` | yes* | `R_` + 15 letters/digits, case-sensitive | *if missing (and `participant.allow_manual_id` is true), the participant must type a valid ID **or** give both a name and an email address — see "Participant IDs" |
| `group` | **yes** | `participant` or `control` (exact, lower case) | missing or misspelt → the study does not start and shows "This link is incomplete" |
| `slot` | **yes** | a whole number, 1 or more (digits only) | slot n uses row ((n − 1) mod 64) + 1 of the group's table in `assignment.json`. **Hand slots out in sequence per group, starting at 1, and never reuse one**: every 64 slots each of the 16 cells (block order × set mapping × order) is used equally often. Missing, `0`, negative, not a whole number → "This link is incomplete" |
| `idate` | no | `YYYY-MM-DD`, a real date | the interview date, added by the researcher who schedules the interviews. Never asked on screen. Invalid → recorded empty |
| `lang` | no | `en` (default) or `ja` | |

Examples:

```
.../?pid=R_9rJJWk01c767jE8&group=participant&slot=1&idate=2026-11-03
.../?pid=R_4EWNe48BIB50mVI&group=control&slot=1&lang=ja
```

Building them from a table (Python), keeping one slot counter per group:

```python
from urllib.parse import urlencode
BASE = 'https://<username>.github.io/<repo-name>/'
next_slot = {'participant': 1, 'control': 1}     # persist this between batches
def link(pid, group, idate=None, lang=None):
    assert group in ('participant', 'control')
    slot = next_slot[group]; next_slot[group] += 1
    q = {'pid': pid, 'group': group, 'slot': slot}
    if idate: q['idate'] = idate          # 'YYYY-MM-DD'
    if lang:  q['lang']  = lang
    return BASE + '?' + urlencode(q)
```

Record which slot went to whom: the slot is also in the data (`slot`,
`assignment_row`), but a slot sent and never used is only in your own
record.

See `SETUP.md` §6 for what to put in the invitation email.

## Things worth knowing

**The package is frozen.** `data/sets/v5b_180/` is byte-identical to the
registered package (`SETUP.md` §5 for the check). Never edit, add, remove,
re-encode, resize or rename anything in it.

**File names match within a session.** The response file
(`<ID>_v5b_180_<stamp>.csv`) and the contact file (`contact_<ID>_<stamp>.csv`)
carry the same stamp: the session start in Japan time. On Pavlovia the
file is `<project>_<ID>_v5b_180_<stamp>_SESSION_<date>.csv` (Pavlovia adds the
outer parts) and there is no contact file. Times inside the
files are UTC; `session_duration_s` and `task_duration_s` give the length
of the session and of the image task (see `DATA_DICTIONARY.md` §1, §5).

**`list_trial_type`, not `trial_type`.** jsPsych writes its own
`trial_type` column holding the plugin name, and overwrites any other value.
The list's `trial_type` is therefore written as `list_trial_type`, next to
the list's `pair_type` (the type of the image pair; the two differ on
consistency and catch rows).

**`item_id` on every trial row.** Responses join to the package's
`items.csv` on `item_id`.

**The chosen image is recorded.** Each row stores `response_side` (`left` /
`right`) and `chosen` (`A` / `B`, from the side and `a_is_left`).

**The background is mid-grey.** The manipulations are colour saturation and
local contrast. A white surround would shift the participant's adaptation
state toward the bright end and compress the differences under study.

**Images are always 512 × 512 CSS pixels** (`display.allow_scaling: false`).
That is why the window check stops, rather than warns, when they do not fit.

## Participant IDs

Format `R_` followed by 15 alphanumeric characters, **case-sensitive**
(`participant.id_pattern`). Normally arrives as `?pid=...` in the URL. The
ID is only checked against that format — it is not looked up anywhere.

**A link without a valid `pid`** (with `participant.allow_manual_id: true`)
still starts. The ID screen then asks for the ID, name and email, says
that all three is best, and will not continue unless the participant gives
**either** a valid ID **or** both a name and a valid email address. An ID
that is typed but does not match the format always blocks Continue (it
would point to the wrong person).

A participant who gives a name and email but no ID gets a unique session
ID, `NOID_DRCHAIN26_` + 8 random characters (prefix:
`participant.no_id_prefix`). It appears in both the response file and the
contact file, so the two still link — but then the contact file is the
only link to the person. With `allow_manual_id: false`, a link without a
`pid` does not start at all.

`Z_21121989` (yours) and `CHAIN_2026` (colleagues) are test IDs. Sessions
using them are flagged `is_test = true` on every row.

## Settings you are most likely to change

In `config.js`:

| Setting | Purpose |
|---|---|
| `platform` | `'auto'` (default: GitHub Pages → `github`, Pavlovia → `pavlovia`, your computer → `local`), or one of those set explicitly |

| `participant.contact_storage` | `'auto'` (default: in the response file on Pavlovia, separate DataPipe file elsewhere), `'datapipe'` or `'results_file'` |
| `debug` | validation report in the console; upload details on the completion screen |
| `blocks.*` | each step on or off (see the session table). Turning a step off removes it; the order of the steps is fixed in `src/main.js`. `blocks.positions` must stay `[1, 2]` on `index.html` |
| `practice` | practice trials and feedback per block position (overrides design.json; now 3 + 3, both with feedback) |
| `timing.rest_ms` | the rest between the blocks (60 000) |
| `participant.allow_manual_id` | set false to require the URL parameter |
| `participant.no_id_prefix` | start of the ID given to sessions without one (`NOID_DRCHAIN26`) |
| `researcher_contact` | shown on the final and upload-failure screens |

The breaks, the catch targets and the block size come from design.json, not
config.js. The wording lives in `text/en/` and `text/ja/`: group-dependent
strings are keyed `participant` / `control`, episode-dependent strings
`derealization` / `ordinary` / `expectation`. Only participants' text may
mention the interview.

## Developer page

Open `dev.html` (e.g. `http://localhost:8000/dev.html`). Choose a **group**
and a **slot** first (chips at the top, or type a slot; the presets stay
disabled until both are valid); the table then shows the slot's assignment
row — episode, set, list and practice file per block. Then a preset or a
custom session:

- full session; **shortened session** (every step, each block cut to its
  first 12 trials); consent; screen; calibration; episode screens;
  episodes + block 1;
- **jump to block 2**, **jump to the rest**, **jump to the word ratings**
  (a marked dev value stands in for the participant's words);
- the first catch trial of block 1; state items; upload test (3 trials per
  block);
- custom: any block switch, either block position, main and practice
  trials per block.

Every dev session is stamped `is_dev = true`; shortened ones also
`shortened = true`, `shortened_to = N`. Shortening exists only here: the
loader ignores `CONFIG.limits` outside dev.html, and `index.html` refuses
to start while they are set. All presets except "Upload test" save locally
instead of uploading. The upload test saves the way the page's platform
does — DataPipe from GitHub Pages or your computer, Pavlovia on Pavlovia.
