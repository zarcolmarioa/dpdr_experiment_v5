# Derealization experiment (v5c, two blocks)

People who have had episodes of derealization see two edited versions of
the same photograph on each trial and press ← or → to choose the one that
looks more like how their surroundings looked during **one specific
episode**. The two versions differ in local contrast (a "fog"-like
reduction), in colour saturation, or in both. A per-person model then
estimates how strongly each person's choices follow each feature:

```
P(chose A) ~ b_sat · pred_sat + b_fog · pred_fog
```

Each session has **two blocks** of 200 trials (180 analysed, 15
consistency repeats, 5 catch trials), each about a different episode:

| group | episodes (order set by the slot) |
|---|---|
| `participant` | **derealization** (the episode they described in the interview) and **ordinary** (one in a similar setting, about as long ago, in which the surroundings looked as usual) |
| `control` | **ordinary** (an episode from the last six months) and **expectation** (how they think the surroundings look to someone experiencing derealization) |

The question above the images depends on the block's episode. Which
episode comes first, which item set (A / B) goes with which episode, and
the trial order are set per invitation by its **slot** (`?slot=n`, row
((n − 1) mod 64) + 1 of the package's `assignment.json`).

The design is registered. The stimuli, the lists, the assignment table and
the catch targets come from the frozen package **`data/sets/v5c_180/`** and
are never randomised, reordered, resampled or regenerated by the
experiment. Each list is shown in file order, with the sides it gives. The
package's `README.txt` describes its pair rules and the five scenes it
excludes (42 scenes are used). The earlier package `data/sets/v5b_180/`
is still in the repository but no longer used; it will be removed
separately.

jsPsych 7.1.2, hosted on GitHub Pages with the data uploaded through
DataPipe to Zenodo — or, from the same files, on Pavlovia with the data
kept in the private Pavlovia project (`SETUP.md` §7). See `SETUP.md` for
deployment and `DATA_DICTIONARY.md` for the output.

## The session

The same order for both groups. Length **[TO COMPLETE after pilot]**. Each
step has its own switch in `config.js`.

| # | step | switch |
|---|---|---|
| 1 | Consent — "I do not agree" ends the session, nothing uploaded | `blocks.consent` (**required** on `index.html`) |
| 2 | Full screen and window check — a window that cannot show the trial layout (each of the session's two questions, two 512 px images) whole **stops** the session (no "continue anyway"), before anything is uploaded | `calibration.fullscreen`, `calibration.screen_check` |
| 3 | Participant ID (+ name and email: on GitHub uploaded separately straight away; on Pavlovia kept in the response file). Without an ID in the link: an ID **or** a name and email are required. On Pavlovia the Pavlovia session opens just before this screen | `participant.collect_*`, `participant.allow_manual_id`, `participant.contact_storage` |
| 4 | Set-up screen (computer on a desk or table, screen at about eye level; no phone or other devices, breaks included), then brightness: maximum brightness, the charger, automatic features (auto brightness, True Tone, Night Shift, blue light filters, battery saver) and steady room lighting, with two required checkboxes. Neither screen mentions the pictures | `calibration.setup`, `calibration.brightness` |
| 5 | Gamma matching (3×) | `calibration.gamma` |
| 6 | Episode selection — participants: the derealization episode, then an ordinary one; controls: an ordinary episode, then the description of derealization. For each recalled episode: a few identifying words, the emotional tone (−3…+3) and the intensity (0–6), all required; when / how long / where, optional (a blank is saved empty) | `blocks.episodes` |
| 7 | **Block 1** — a reinstatement screen naming the episode with the participant's own words; the task explained for the block's episode; 3 practice trials with feedback (the first with arrows under the images, then only the chosen image and a message for 3 s, `timing.first_feedback_ms`; the others with the chosen image outlined); 200 trials, breaks after 40, 80, 120 and 160 ("n of 200") | `blocks.practice`, `blocks.main` |
| 8 | Rest — 1 minute, countdown; Continue appears at zero | `blocks.rest`, `timing.rest_ms` |
| 9 | **Block 2** — as block 1, with the second episode; its practice intro says the question has changed, shows it and restates the task for that episode | as block 1 |
| 10 | Word ratings — 10 words, 0–6 (participants: the derealization episode; controls: their expectation) | `blocks.words` |
| 11 | CDS items 2, 13, 19 and 29 (trait format, verbatim): the frequency (0 to 4), then, when it is not 0, the duration (1 to 6) | `blocks.cds` |
| 12 | Save (DataPipe / Pavlovia / download), completion screen (no contact sentence; the upload-failure screen keeps the contact address) | `platform` (`'auto'`: from the address) |

The set-up screen and the instructions before block 1's practice ask
participants not to reload or close the page until the final screen; from
the consent screen to the final screen the browser's own "Leave this
page?" dialog guards against it (see **Interruptions** below).

The images (617 of them, ≈ 223 MB, both blocks, block 1's first) start downloading in
the background right after the ID screen, so they are usually cached by
the time each block needs them. There are no questions after the blocks.

**Practice** comes from the package alone (design.json
`practice_by_block`, `practice_feedback_by_block_position`,
`practice_feedback_trials`, and the practice files; there is no override
in config.js): 3 trials before each block, all with feedback — the 3 rows
of `practice/block1.json` before block 1, the 3 rows of
`practice/block2.json` before block 2. The practice file follows the block
position, not the episode. A package without these keys does not start.

**Catch trials** show no images; their targets come from design.json by
block position, restarting in each block. Failures are recorded per block;
the exclusion rule (3 or more over the session) is applied in the
analysis.

## Interruptions: resuming, and the completion check

`src/progress.js`. Everything here works **in the same browser only**: the
progress is kept in that browser's storage (localStorage), and nothing is
sent anywhere until the usual upload at the end.

**Resuming after a reload or a closed tab.** After every screen and trial
the page stores its progress and every response. Opening the same link
again (same participant ID, group, slot, package and experiment version)
shows a screen saying the study was interrupted, with only **Continue**.
Continuing needs full screen again (and passes the window check again) and
waits for the images, as at the start. Where it continues:

| interrupted during | continues with |
|---|---|
| consent, participant details, full screen, set-up, brightness or screen calibration | that part again from its first screen |
| the episode questions | the episode questions from the first episode screen |
| a block's practice | the reinstatement screen, the practice instructions, then the practice from its first trial |
| the end-of-practice screen | the reinstatement screen, then that screen |
| the main trials | the reinstatement screen, then the exact trial where the person stopped |
| a break | that break screen |
| the rest | the rest screen, with the time that remained |
| the word ratings or the CDS items | that part again from its first screen (the words keep their order) |
| the saving step | the saving step, under a distinct file name (`…_resumed<n>.csv`, recorded as `data_filename`) |

The assignment, lists, order, catch targets and breaks continue exactly as
before. Trials and screens completed before the interruption are kept and
appear **once** in the final file; answers from a screen that is started
again are dropped, and the restart is recorded. The name and email upload
is **not repeated** if it had succeeded before the interruption
(`contact_saved_before_resume` on the `resume` row). No time limit is
enforced: every interruption is recorded (`resume` rows, `segment`,
`resume_count`, `DATA_DICTIONARY.md` §16) and the analysis decides. A link
opened with other values starts normally.

If the browser has no usable storage (blocked by its settings, or a write
fails), the study runs normally without resuming and records
`resume_available = false`. A private window does have storage until it is
closed, so a reload in a private window resumes, but closing the window
loses the progress.

**Completion check.** When the final screen appears (saved, or the
upload-failure screen with its download button), the stored progress is
deleted and the browser records that this participant ID has completed the
study (for this experiment name). Opening the link again in that browser
shows only: *"You have already completed this study. Thank you for your
participation."* A typed ID is checked straight after the ID screen,
before anything is uploaded. **Sessions without a participant ID (name and
email only) cannot be recognised**, and neither can a participant who opens
the link in another browser or on another device. The check also applies
to the test IDs; clear it from `dev.html` (below).

**"Leave this page?"** From the consent screen until the final screen,
reloading or closing the tab triggers the browser's own dialog (its wording
is the browser's). Browsers show it only after the person has clicked or
typed on the page, so not on the consent screen before the first click. It
is switched off on the final screen, and on the screens that end a session
early (consent declined, window too small).

## Invitation links

Each participant gets their own link. All parameters are read in the
browser and never reach the server.

```
https://<username>.github.io/<repo-name>/?pid=<ID>&group=<group>&slot=<n>&idate=<YYYY-MM-DD>
https://run.pavlovia.org/<user>/<project>/?pid=<ID>&group=<group>&slot=<n>&idate=<YYYY-MM-DD>
```

The same parameters on both.

| parameter | required | values | notes |
|---|---|---|---|
| `pid` | yes* | `R_` + 15 letters/digits, case-sensitive | *if missing (and `participant.allow_manual_id` is true), the participant must type a valid ID **or** give both a name and an email address — see "Participant IDs" |
| `group` | **yes** | `participant` or `control` (exact, lower case) | missing or misspelt → the study does not start and shows "This link is incomplete" |
| `slot` | **yes** | a whole number, 1 or more (digits only) | slot n uses row ((n − 1) mod 64) + 1 of the group's table in `assignment.json`. **Hand slots out in sequence per group, starting at 1, and never reuse one**: every 64 slots each of the 16 cells (block order × set mapping × order) is used equally often. Missing, `0`, negative, not a whole number → "This link is incomplete" |
| `idate` | no | `YYYY-MM-DD`, a real date | the interview date, added by the researcher who schedules the interviews. Never asked on screen. Invalid → recorded empty |
| `lang` | no | `en` (default) or `ja` | |

Examples:

```
.../?pid=R_9rJJWk01c767jE8&group=participant&slot=1&idate=2026-11-03
.../?pid=R_4EWNe48BIB50mVI&group=control&slot=1&lang=ja
```

Building them from a table (Python), keeping one slot counter per group:

```python
from urllib.parse import urlencode
BASE = 'https://<username>.github.io/<repo-name>/'
next_slot = {'participant': 1, 'control': 1}     # persist this between batches
def link(pid, group, idate=None, lang=None):
    assert group in ('participant', 'control')
    slot = next_slot[group]; next_slot[group] += 1
    q = {'pid': pid, 'group': group, 'slot': slot}
    if idate: q['idate'] = idate          # 'YYYY-MM-DD'
    if lang:  q['lang']  = lang
    return BASE + '?' + urlencode(q)
```

Record which slot went to whom: the slot is also in the data (`slot`,
`assignment_row`), but a slot sent and never used is only in your own
record.

See `SETUP.md` §6 for what to put in the invitation email.

## Things worth knowing

**The packages are frozen.** `data/sets/v5c_180/` was verified against the
package's checksums when it was committed (`SETUP.md` §5 for the check).
Never edit, add, remove, re-encode, resize or rename anything in it, or in
`data/sets/v5b_180/`.

**File names match within a session.** The response file
(`<ID>_v5c_180_<stamp>.csv`) and the contact file (`contact_<ID>_<stamp>.csv`)
carry the same stamp: the session start in Japan time. On Pavlovia the
file is `<project>_<ID>_v5c_180_<stamp>_SESSION_<date>.csv` (Pavlovia adds the
outer parts) and there is no contact file. Times inside the
files are UTC; `session_duration_s` and `task_duration_s` give the length
of the session and of the image task (see `DATA_DICTIONARY.md` §1, §5).

**`list_trial_type`, not `trial_type`.** jsPsych writes its own
`trial_type` column holding the plugin name, and overwrites any other value.
The list's `trial_type` is therefore written as `list_trial_type`, next to
the list's `pair_type` (the type of the image pair; the two differ on
consistency and catch rows).

**`item_id` on every trial row.** Responses join to the package's
`items.csv` on `item_id`.

**The chosen image is recorded.** Each row stores `response_side` (`left` /
`right`) and `chosen` (`A` / `B`, from the side and `a_is_left`).

**The background is mid-grey.** The manipulations are colour saturation and
local contrast. A white surround would shift the participant's adaptation
state toward the bright end and compress the differences under study.

**Images are always 512 × 512 CSS pixels** (`display.allow_scaling: false`).
That is why the window check stops, rather than warns, when they do not fit.

## Participant IDs

Format `R_` followed by 15 alphanumeric characters, **case-sensitive**
(`participant.id_pattern`). Normally arrives as `?pid=...` in the URL. The
ID is only checked against that format — it is not looked up anywhere.

**A link without a valid `pid`** (with `participant.allow_manual_id: true`)
still starts. The ID screen then asks for the ID, name and email, says
that all three is best, and will not continue unless the participant gives
**either** a valid ID **or** both a name and a valid email address. An ID
that is typed but does not match the format always blocks Continue (it
would point to the wrong person).

A participant who gives a name and email but no ID gets a unique session
ID, `NOID_DRCHAIN26_` + 8 random characters (prefix:
`participant.no_id_prefix`). It appears in both the response file and the
contact file, so the two still link — but then the contact file is the
only link to the person. With `allow_manual_id: false`, a link without a
`pid` does not start at all.

`Z_21121989` (yours) and `CHAIN_2026` (colleagues) are test IDs. Sessions
using them are flagged `is_test = true` on every row.

## Developer page

Open `dev.html` (e.g. `http://localhost:8000/dev.html`). Choose a **group**
and a **slot** first (chips at the top, or type a slot; the presets stay
disabled until both are valid); the table then shows the slot's assignment
row — episode, set, list and practice file per block. Then a preset or a
custom session:

- full session; **shortened session** (every step, each block cut to its
  first 12 trials); consent; screen; calibration; episode screens;
  episodes + block 1;
- **jump to block 2**, **jump to the rest**, **jump to the word ratings**
  (a marked dev value stands in for the participant's words);
- the first catch trial of block 1; CDS items; upload test (3 trials per
  block);
- custom: any block switch, either block position, main and practice
  trials per block.

**Trial label.** The "Trial label" box (ticked by default) shows a small
label under the images on every practice and main trial (catch trials: at
the bottom of the screen), e.g. `Block 1 · 37/200 · sat_only · A016 · A on
left · colour +1.03 SD, contrast +0.00 SD`. Colour and contrast are the
list's `pred_sat` and `pred_fog` (positive = image A is the predicted
choice); consistency rows add `repeat of trial n`, catch rows their target.
A second line gives each image's levels, read from its file name
(`<scene>__c<level>__s<level>.png`: `c` contrast, `s` saturation; `0`,
`p1`–`p3`, `n1`–`n3`) and how far apart they are, e.g. `Left: contrast −2,
colour +1 · Right: contrast −2, colour −3 · Apart: contrast 0, colour 4
levels`; an unedited image (`c0`, `s0`) reads `original`. Catch rows show
no images, so they have only the first line. On `dev.html` the validator
checks that every image a list or practice file shows follows that name
pattern. The label is drawn after each screen appears, so it is not recorded in any
column (including `stimulus`). It never appears on `index.html`, and
`index.html` refuses to start if `CONFIG.dev.trial_label` is true.
`node tools/test_trial_label.js` checks all of this in a browser.

**Stored in this browser.** The menu lists what this browser holds for the
study: an unfinished dev session for the current link can be **resumed**
(with the dev settings it was started with), and one button **clears all
stored progress and completion records**. dev.html and index.html share the
browser's storage (same address), so this also clears what index.html runs
left, for example the completion record of a test ID. A preset starts a
new session for the link, replacing its stored progress. dev.html never
applies the completion check.

Every dev session is stamped `is_dev = true`; shortened ones also
`shortened = true`, `shortened_to = N`. Shortening exists only here: the
loader ignores `CONFIG.limits` outside dev.html, and `index.html` refuses
to start while they are set. All presets except "Upload test" save locally
instead of uploading. The upload test saves the way the page's platform
does — DataPipe from GitHub Pages or your computer, Pavlovia on Pavlovia.
